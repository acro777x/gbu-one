1. EXECUTIVE SUMMARY & ARCHITECTURAL PHILOSOPHY
--------------------------------------------------------------------------------
Gautam Buddha University (GBU), situated across 511 green acres in Greater Noida, Uttar Pradesh, is home to thousands of undergraduate, postgraduate, and doctoral scholars across eight distinct academic schools:
  1. School of Information and Communication Technology (SOICT)
  2. School of Engineering (SOE)
  3. School of Biotechnology (SOBT)
  4. School of Management (SOM)
  5. School of Law, Justice and Governance (SOLJG)
  6. School of Humanities and Social Sciences (SOHSS)
  7. School of Vocational Studies and Applied Sciences (SOVSAS)
  8. University Administration & Examination Division (ADMIN)

Historically, students and faculty operated within a fragmented information landscape. Crucial academic schedules, room shifts, examination datesheets, circulars, previous year examination papers, and grade announcements were dispersed across disparate, slow, non-responsive portals, physical department notice boards, and informal messaging channels. This created widespread confusion, attendance loss, and academic anxiety.

GBU One and GBU One Admin were architected from first principles to resolve these pain points. The ecosystem establishes a single, unified, offline-first digital companion tailored specifically to GBU's physical and digital topology.

The fundamental core architectural tenets governing the platform are:

A. STRICT OFFLINE-FIRST ARCHITECTURE:
Campus connectivity across lecture halls, basements, and hostel corridors is notoriously unpredictable. Therefore, neither GBU One nor GBU One Admin ever treats the network as a prerequisite. Every screen, including Timetable, Notices, PYQ Library, Examination Date Sheets, Events, and Settings, renders instantly from local storage (expo-sqlite, MMKV, and AsyncStorage) with zero layout shifts. Network requests execute transparently in the background, invalidating stale caches and applying non-disruptive optimistic updates.

B. ZERO-BARRIER GUEST ACCESS:
Forcing students to undergo lengthy sign-up flows or account verification before accessing their next class room number, an urgent bus circular, or an exam date is hostile to user experience. GBU One offers full, first-class functionality in Guest Mode. Guests can browse schedules, receive class alarms, search circulars, download papers, and even contribute question papers to the university library. An auto-generated persistent student identity (GBU-XXXXXX) tracks guest contributions, and upon account creation, seamlessly transfers all accrued stats and identity markers without data loss.

C. CREDENTIAL HONESTY & PRIVACY ASSURANCE:
Under no circumstances does GBU One or GBU One Admin prompt for, log, transmit, or cache a student's official university password. Webmail and ERP portal integrations function via clean sandbox viewports and direct URL delegations. The app account utilizes independent, secure credentials, guaranteeing that student credentials cannot be intercepted, compromised, or mishandled.

D. DUAL-APPLICATION BIFURCATION (STUDENT VS. ADMIN):
Rather than bloating the student application with administrative checks and dormant management logic, the codebase compiles into two distinct, hermetically isolated application packages:
  - in.gbu.one (Student Public APK): Purged of all administrative routes, secrets, and management controls, achieving minimum bundle size, rapid cold-start times, and zero attack surface.
  - in.gbu.one.admin (Administrative APK): Equipped with server-side Supabase Auth, moderation pipelines, date sheet ingestors, notice broadcasters, and emergency offline access controls.

E. LIGHT-FIRST DESIGN & TACTILE ACCESSIBILITY:
Per the UI specification, GBU One adopts a radiant, modern light theme by default, featuring high-contrast typography, warm cream and glassmorphic card surfaces, university brand accents, and a minimum 44pt touch target across all interactive controls. Dark mode is dynamically supported for low-light hostel study sessions, adhering strictly to WCAG AA contrast standards.

3. DETAILED ADMIN CONSOLE (GBU ONE ADMIN) SPECIFICATION
--------------------------------------------------------------------------------
The GBU One Admin application (package: in.gbu.one.admin) is a dedicated command and control terminal designed for university deans, examination coordinators, department heads, and authorized system administrators.

3.1 HARDENED SECURITY GATEWAY & HYBRID AUTHENTICATION (app/admin/index.tsx)
Access to the administrative console is protected by an enterprise-grade dual-tier security architecture:
  - Tier 1: Server-Side Supabase Authentication:
      Administrators authenticate using an authorized university administrative email and password. Credentials are authenticated directly against Supabase GoTrue Auth, returning a signed JWT with strict role claims.
  - Tier 2: FIPS 180-4 Cryptographic PIN & Local Master Auth:
      For emergency offline access or rapid terminal unlocks, the system implements a SHA-256 hashed PIN gateway. PINs are salted and hashed using an audited TypeScript NIST implementation before comparison against secure storage.
  - Brute-Force Lockout Defense:
      An automated exponential backoff mechanism limits consecutive invalid attempts. After 5 failed attempts, the console locks out for 5 minutes, rendering a live countdown timer and logging the intrusion attempt to the audit ledger.

3.2 HORIZONTAL SCROLLABLE WORKSPACE TABS
To prevent UI clipping and provide seamless navigation across dense operational workflows, the Admin Console features a horizontal scrollable tab header equipped with tactile feedback:
  - Tab 1: Events (Campus Event Publishing & Gallery Moderation)
  - Tab 2: Notices (University Circular Publisher & Emergency Broadcasts)
  - Tab 3: Datesheets (Exam Datesheet Ingestion, Editing & Shift Alerts)
  - Tab 4: PYQ Queue (Crowdsourced Question Paper Moderation & Verification)
  - Tab 5: Update Manager (Compulsory App Update Management & Rollback)
  - Tab 6: Audit Log (Cryptographic Action Ledger & Security Monitor)

3.3 CAMPUS EVENTS MANAGEMENT (ADMIN TAB 1)
Allows administrative coordinators to broadcast official fests, workshops, and sports tournaments:
  - Event Creation Form: Fields for Event Title, Organizing Club/School, Venue Location (Main Auditorium, Indoor Stadium, SOICT Seminar Hall), Start Date/Time, and RSVP link.
  - High-Resolution Poster Upload: Direct integration with Supabase Storage (`event-photos` bucket) with automated JPEG compression.
  - Live Event Feed: Real-time list of active campus events with one-tap archival or deletion controls.

3.4 NOTICE & CIRCULAR PUBLISHER (ADMIN TAB 2)
The authoritative channel for distributing official university circulars:
  - Multi-School Targeting: Broadcasters can target circulars globally to all schools or restrict visibility to specific faculties (e.g., SOICT only or SOE only).
  - Category Assignment: Classify as Examination, Urgent Administration, Hostel/Mess, Fee, Sports, or Cultural.
  - Attachment Dispatcher: Upload official signed circular PDFs directly to the `notice-attachments` Supabase bucket.
  - Emergency Priority Flag: Toggling 'Urgent Priority' highlights the circular in red across all student Home and Notice feeds, triggering immediate push notification dispatch.

3.5 DATESHEET INGESTION & SCHEDULE CONTROLLER (ADMIN TAB 3)
A robust management tool for university examination controllers:
  - Ingestion Modes: Supports manual form entry or rapid bulk JSON paste for entire semester examination datesheets.
  - Conflict Detection: Validates that no student group has overlapping examinations scheduled in the same shift.
  - Real-Time Shift Broadcast: If an examination is rescheduled (e.g., room change or date postponement), the admin console broadcasts a high-priority schedule update alert to all affected students.

3.6 PYQ MODERATION QUEUE & VERIFICATION PIPELINE (ADMIN TAB 4)
The operational heart of academic quality assurance:
  - Real-Time Pending Counter: Live badge indicating unreviewed student submissions (e.g., 'PYQ (14)').
  - Detailed Paper Inspection Card:
      * Subject Code & Name: Displays course metadata entered by the contributor.
      * Exam Type & Year: Verifies Mid Sem, End Sem, or Back Paper categorization.
      * Uploader Identity & Metadata: Renders the contributor's Unique Student ID (e.g., `GBU-21ICS045`), selected avatar, and submission timestamp.
      * Contributor Guest vs. Auth Status: Clearly indicates whether the submission came from an authenticated student or a guest device.
  - Integrated PDF Preview: Administrators can inspect the uploaded document directly within the app to ensure legible scan quality, complete pages, and academic relevance.
  - One-Tap Approval & Point Awarding:
      * Approving a paper automatically moves the PDF from `pyq-pending` to `pyq-papers` public storage.
      * Increments the verified paper count in the database.
      * Awards 50 contribution points to the uploader's profile or device ID.
      * Automatically triggers leaderboard podium recalculation.
  - Rejection with Reason: Administrators can reject illegible or irrelevant files, removing the quarantine file and notifying the user.

3.7 COMPULSORY APP UPDATE & BROADCAST MANAGER (ADMIN TAB 5)
An enterprise release management system empowering administrators to push required app updates or revert problematic releases:
  - Release Configuration Controls:
      * Latest Version Input (e.g., `1.0.1`): Sets the current production release string.
      * Minimum Supported Version Input (e.g., `1.0.0`): Sets the floor version required to run the app.
      * Compulsory / Mandatory Mode Switch: When toggled ON, any student app running a version lower than the minimum version displays a non-dismissible, full-screen blocking modal requiring APK update.
      * Direct APK Download URL: Points to official university GitHub Releases or cloud CDN hosting the compiled APK.
      * Release Highlights: Multi-line text field detailing new features, bug fixes, and critical security updates.
  - Broadcast Version Update Action: Publishes the update manifest to Supabase `app_versions` table, instantly alerting student devices.
  - Instant Revert to Default: An emergency fail-safe button that instantly restores the manifest to baseline (`1.0.0`, Non-Mandatory), unblocking all student devices in the event of an erroneous broadcast.
  - Historical Broadcast Feed: A persistent, scrollable ledger rendering all historical update pushes with timestamp, version strings, mandatory status, and admin author ID.

3.8 SHA-256 CRYPTOGRAPHIC AUDIT LEDGER (ADMIN TAB 6)
To satisfy institutional accountability and prevent unauthorized actions:
  - Append-Only Hash Chain: Every administrative action (notice published, paper approved, update pushed, lockout triggered) is hashed using SHA-256 and linked to the previous entry's hash.
  - Immutable Audit Log: Records admin ID, IP/device signature, action type, target entity ID, and timestamp.
  - Export Audit Report: Generates a signed cryptographic summary report for university executive leadership.

4. CORE TECHNICAL IMPLEMENTATION & CODE ARCHITECTURE
--------------------------------------------------------------------------------
The GBU One ecosystem is constructed upon a modern, modular React Native architecture leveraging Expo SDK 52 with the New Architecture enabled.

4.1 EXPO ROUTER V4 FILE-SYSTEM ROUTING
The navigation layer utilizes Expo Router v4, establishing strict type-safety, deep-linking, and URL-based navigation:
  - Root Layout (`app/_layout.tsx`): Initializes global React Query providers, font loaders (Poppins, Inter), SQLite databases, push notification listeners, and the mandatory update interceptor modal.
  - Tab Hierarchy (`app/(tabs)/_layout.tsx`): Configures custom high-contrast bottom navigation tabs with animated SVG icons, haptic feedback, and dynamic active indicators.
  - Modal & Stack Routes:
      * `app/pyq/leaderboard.tsx`: Dedicated full-screen leaderboard route.
      * `app/pyq/upload.tsx`: Full-screen paper submission workflow.
      * `app/admin/index.tsx`: Dedicated administrative console (strictly isolated to the Admin APK).
      * `app/exams.tsx`, `app/calendar.tsx`, `app/events.tsx`, `app/mail.tsx`, `app/pdf.tsx`: Feature-specific stack screens.

4.2 COMPONENT ISOLATION & ZERO NATIVE MODAL ENFORCEMENT
A critical architectural triumph of the codebase is the total elimination of React Native's built-in `<Modal>` component. In standard React Native applications, native modals frequently cause severe z-index clipping, keyboard dismissal flickers, and backdrop freezing on modern Android versions (Android 14/15).
GBU One enforces an architectural rule verified by automated AST tests (`tests/no_native_modal.test.ts`):
  - Zero Native Modals: Every popup, dialog, bottom sheet, and action menu is implemented using absolute-positioned glassmorphic overlay views managed by animated timing curves and flexbox layouts.
  - Absolute Positioning Overlays: Components render cleanly within React's virtual DOM tree, guaranteeing 100% reliable touch handling, smooth hardware-accelerated animations, and zero keyboard collision bugs.

4.3 STATE MANAGEMENT & TANSTACK REACT QUERY V5
The application balances local UI state with asynchronous server state:
  - Local State via Zustand:
      * `useAuthStore`: Manages authenticated session tokens, user roles, guest mode status, and student credentials.
      * `useIdentityStore`: Manages the device unique student ID (`GBU-XXXXXX`), selected avatar persona, and guest profile attributes.
      * `useClassStore`: Stores active school, programme, semester, and section preferences.
      * `useThemeStore`: Controls light/dark/system theme states with instantaneous re-rendering.
  - Server State via TanStack Query v5:
      * Automatic Stale-While-Revalidate: Fetches timetable data, notices, and PYQ catalogs from local SQLite cache instantly, while silently polling Supabase in the background.
      * Query Invalidation: Approving a paper or publishing an update instantly invalidates relevant query keys (`['pyq-papers']`, `['app-version']`, `['notices']`), updating screens without manual user refreshes.

4.4 HIGH-PERFORMANCE FLATLIST TUNING
To maintain buttery 60 FPS scrolling across budget Android devices (such as MediaTek Helio or Dimensity chipsets) while displaying hundreds of circulars or question papers:
  - Window Size Optimization: FlatLists configure `windowSize={5}`, `initialNumToRender={8}`, and `maxToRenderPerBatch={10}`.
  - Memory Pruning: `removeClippedSubviews={true}` actively unmounts off-screen elements, maintaining low memory footprints.
  - Stable Key Extractors: All items bind to unique database UUIDs or subject codes (`keyExtractor={(item) => item.id}`).
  - Memoized Renderers: List item cards are wrapped in `React.memo` with shallow equality comparators to prevent unnecessary re-renders when parent states change.

4.5 MULTI-TIER STORAGE ARCHITECTURE
GBU One deploys three synchronized storage tiers:
  1. Tier 1: Next-Gen SQLite (`expo-sqlite`): Structured relational database storing thousands of timetable schedules, historical circulars, and the complete 841+ PYQ catalogue for offline instant querying.
  2. Tier 2: MMKV Key-Value Storage: Ultra-fast C++ binary storage for rapid access to active tokens, user preferences, and theme choices.
  3. Tier 3: AsyncStorage Fallback: Universal cross-platform storage fallback ensuring complete data resilience across varied Android ROMs.

5. BACKEND ARCHITECTURE, SUPABASE & WORKER PIPELINES
--------------------------------------------------------------------------------
The backend infrastructure is built on Supabase Cloud, delivering high-availability PostgreSQL 15, PostgREST API endpoints, Row Level Security (RLS), and scalable S3-compatible Object Storage.

5.1 SUPABASE DATABASE ENTITIES & ROW LEVEL SECURITY (RLS)
The database enforces strict, least-privilege security policies via PostgreSQL RLS:
  - `profiles`: Stores authenticated student profiles, roles (`student` vs. `admin`), selected avatar IDs, and accumulated PYQ contribution points. Students can read all public profiles but can only update their own.
  - `timetable_entries`: Contains structured lecture schedules categorized by school, programme, semester, section, subject code, room number, faculty, day of week, and shift times. Read-only for students; writable exclusively by authenticated administrators.
  - `notices`: Stores official university circulars, school targets, category tags, PDF attachment URLs, and priority flags. Read-only for students; writable exclusively by administrators.
  - `pyq_papers`: The verified public question paper repository. Publicly readable by all students and guests; insertable and updatable only by the administrative moderation pipeline.
  - `pyq_pending`: The quarantine ingestion table for new submissions. Writable by any user (students and guests); readable and actionable solely by verified administrators.
  - `events`: Campus events and photo memories. Publicly readable; managed by admin accounts.
  - `app_versions`: Version release manifests. Publicly readable by all clients; updatable strictly by admin accounts with full audit logging.
  - `audit_ledger`: Append-only cryptographic ledger recording all administrative actions. Writable only via authenticated security functions.

5.2 BACKGROUND INGESTION WORKERS (`/worker`)
An automated Node.js 20 LTS TypeScript worker daemon runs periodically via GitHub Actions cron or server container:
  - University Timetable Poller (`worker/src/timetable.ts`):
      * Fetches published timetable matrices from university servers and departmental spreadsheets.
      * Computes cryptographic hash diffs against existing database rows.
      * Ingests schedule changes and generates room-shift alert payloads.
  - Official Notices Scraper (`worker/src/notices.ts`):
      * Scrapes public GBU circular portals (`gbu.ac.in/notices`) at polite, rate-limited intervals using a custom identifiable User-Agent.
      * Extracts circular metadata, title, publication date, and downloadable PDF URLs.
      * Performs OCR text extraction on scanned image circulars, allowing full-text search across previously unsearchable documents.
      * Dispatches high-priority push notifications when emergency circulars are detected.
  - Examination Results Watcher (`worker/src/results.ts`):
      * Monitors the university examination grading portal for new semester results announcements.
      * Alerts enrolled students the moment their branch's grade cards become available.

6. SECURITY ARCHITECTURE, CRYPTOGRAPHY & IDENTITY MIGRATION
--------------------------------------------------------------------------------
Security is paramount in the GBU One platform, protecting user privacy, administrative integrity, and system availability.

6.1 SERVER-SIDE RBAC & JWT TOKEN VERIFICATION
Administrative operations are strictly verified on the Supabase server:
  - Role Claims: When an admin authenticates via Supabase Auth, their JWT token contains an explicit role attribute (`role: 'admin'`).
  - Row Level Security Enforcement: PostgREST evaluates PostgreSQL policies (`auth.jwt() ->> 'role' = 'admin'`) before permitting any insert, update, or delete on sensitive tables (`pyq_papers`, `app_versions`, `notices`).
  - Client-Side Bypass Immunity: Even if an attacker were to modify client-side APK code or bypass local PIN screens, all unauthorized backend requests are rejected with HTTP 403 Forbidden by the database engine.

6.2 AUDITED NIST SHA-256 TYPESCRIPT CRYPTOGRAPHIC ENGINE
For offline administrative authentication and audit logging, GBU One implements a standalone NIST FIPS 180-4 compliant SHA-256 cryptographic module (`src/lib/sha256.ts`):
  - Pure TypeScript Implementation: Contains zero external binary or Node-native crypto dependencies, guaranteeing 100% consistent execution across Android, iOS, and Jest test environments.
  - 32-Bit Bitwise Math: Employs standard 32-bit big-endian word operations (`Ch`, `Maj`, `Sigma0`, `Sigma1`, `sigma0`, `sigma1`) with complete round constant arrays ($K$).
  - Salted Hash Storage: PINs and sensitive identifiers are salted with a 32-character high-entropy secret before hashing.

6.3 BRUTE-FORCE LOCKOUT & EXPONENTIAL BACKOFF
To defeat automated PIN guessing or unauthorized device tampering:
  - Failed Attempt Tracking: Consecutive failed attempts are recorded in persistent secure storage (`@gbu_admin_lockout_state`).
  - Threshold Lockout: Upon the 5th consecutive failure, the console locks out for 300 seconds (5 minutes).
  - Real-Time Countdown: The UI displays an active countdown timer, disabling all input fields until the lockout interval expires.
  - Immutable Security Logging: Every lockout event generates an entry in the cryptographic audit ledger.

6.4 HASH-CHAINED CRYPTOGRAPHIC AUDIT TRAIL
Every administrative state change (e.g., paper approval, version update push, circular broadcast) is recorded in an immutable hash chain:
  - Hash Chain Architecture: Each log entry stores `previous_hash`, `timestamp`, `admin_id`, `action`, `payload_hash`, and its own `current_hash = SHA256(previous_hash + timestamp + admin_id + action + payload_hash)`.
  - Tamper Evidence: Any retroactive modification or deletion of an audit record invalidates all subsequent hash signatures in the chain, immediately exposing tampering during verification audits.

6.5 GUEST IDENTITY PERSISTENCE & CLOUD MIGRATION
To reconcile zero-barrier guest access with long-term user accounts:
  - Hardware-Anchored Device ID: On initial launch, guest devices generate a persistent unique ID (`GBU-XXXXXX`) using random alphanumeric entropy, saved to MMKV storage.
  - Contribution Attribution: All paper uploads and activity logs submitted during guest sessions bind to this unique device ID.
  - Atomic Cloud Migration: When the user subsequently signs up for an official account, the client executes an atomic Supabase RPC (`transfer_guest_profile`), updating all prior submissions, earned leaderboard points, and avatar preferences from the guest ID to the new authenticated user UUID. No student ever loses points accrued while in guest mode.

12.8 ATOMIC PL/PGSQL MIGRATION FUNCTIONS
```sql
-- Atomic Guest Profile Transfer Function
CREATE OR REPLACE FUNCTION public.transfer_guest_profile(
  p_guest_id VARCHAR(16),
  p_user_id UUID
) RETURNS VOID AS $$
BEGIN
  -- Link all approved papers
  UPDATE public.pyq_papers
  SET uploader_auth_id = p_user_id
  WHERE uploader_unique_id = p_guest_id;

  -- Link all pending submissions
  UPDATE public.pyq_pending
  SET uploader_auth_id = p_user_id
  WHERE uploader_unique_id = p_guest_id;

  -- Sync points to profile
  UPDATE public.profiles
  SET pyq_points = (
    SELECT COUNT(*) * 50 FROM public.pyq_papers WHERE uploader_unique_id = p_guest_id
  ),
  verified_papers_count = (
    SELECT COUNT(*) FROM public.pyq_papers WHERE uploader_unique_id = p_guest_id
  )
  WHERE id = p_user_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

14. DEPLOYMENT PLAYBOOK & MAINTENANCE GUIDE
--------------------------------------------------------------------------------
14.1 RUNNING TESTS & TYPECHECKING
Before creating any release build, execute the following commands in the workspace root:
  - Run TypeScript Typecheck:
      npx tsc --noEmit
    (Ensure 0 errors are emitted).
  - Run Complete Test Suite:
      npm test
    (Ensure all 38 test suites and 626 tests pass).
  - Run Code Linter:
      npm run lint

14.2 COMPILING RELEASES
  - Compiling the Student APK:
      python tools/build_android_apk.py
    Output artifact: `apk/gbu-one.apk`
  - Compiling the Admin APK:
      python tools/build_admin.py
    Output artifact: `apk/gbu-one-admin.apk`

14.3 INSTALLING TO PHYSICAL DEVICES VIA ADB
With your Android device connected via USB with USB Debugging enabled:
  - Install Student APK:
      adb -s <DEVICE_ID> install -r apk/gbu-one.apk
  - Install Admin APK:
      adb -s <DEVICE_ID> install -r apk/gbu-one-admin.apk
  - Launch Student App:
      adb -s <DEVICE_ID> shell am start -n in.gbu.one/in.gbu.one.MainActivity
  - Launch Admin App:
      adb -s <DEVICE_ID> shell am start -n in.gbu.one.admin/in.gbu.one.MainActivity

14.4 DATABASE INITIALIZATION & MIGRATIONS
When deploying to a fresh Supabase project:
  1. Open the Supabase SQL Editor dashboard.
  2. Copy and paste the entire contents of `supabase/schema.sql`.
  3. Execute the script to initialize tables, RLS policies, triggers, and functions.
  4. Launch the Admin Console (`in.gbu.one.admin`), navigate to 'Initial Setup', and register the primary owner administrator account.
